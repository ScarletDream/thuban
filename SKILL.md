# Thuban

Build the smallest evidence-backed control map that lets future agents make correct local decisions. A Thuban node is a decision contract, not a directory README or universal handoff.

## Govern

1. Resolve the exact owned scope. Read applicable `AGENTS.md`, manifests, entry points, existing instructions, and the minimum evidence for the next decision.
2. Use ownership, structure plasticity, and error cost; the most conservative axis caps action:
   - **Shape** a new or still-plastic owned area.
   - **Overlay** a mature area without broad restructuring.
   - **Boundary** an external, generated, vendored, or unowned area from its nearest owned parent.
3. Find the highest-value drift or repeated decision cost. Classify areas and durable documents as keep, refactor, archive, clean, or investigate. Prefer an existing subject owner; before consolidation, cleaning, or bulk-moving, verify exact targets, consumers, authority, and recovery.
4. Create or repair one root `THUBAN.md` for the adopted scope. A project may contain multiple local `THUBAN.md` nodes; add one only for a real governance boundary with enough independent contract, state, or routing cost to repay it.
5. Assign truth by subject: verified reality, intent, instructions, or history. Resolve conflicts with evidence; newer prose does not win automatically.
6. Keep state at the narrowest node that owns its consequences. Root state contains only project-level consequences; do not manufacture one global current-state document.
7. Validate routes, claimed paths, instruction precedence, postconditions, and zero-diff behavior before reporting.

Read [THUBAN-PROTOCOL.md](references/THUBAN-PROTOCOL.md) before creating, splitting, merging, repairing, or auditing Thuban nodes; changing their authority or topology; proposing an `AGENTS.md` bootstrap; or consolidating, archiving, or cleaning durable project documents as governance work.

## Authority

Treat the current user as authorizer for in-scope work unless evidence establishes a narrower owner. Default to read-only. Show an exact preview and obtain approval before changing `AGENTS.md`, scope, authority, durable constraints, topology, directory structure, or destructive disposition. One authorization is not continuing authority.

Use the lightest approval posture that preserves authority: notify only for read-only findings and zero diff; combine related local-governance changes into one conclusion-first packet with the exact write set, authority effect, and excluded actions; keep external writes, destructive disposition, new cost, and access or permission changes action-specific. One approval covers the shown packet. Do not fragment it by file or by consequence-equivalent step.

By default, adoption writes only the required Thuban nodes and one managed bootstrap. Add an existing file to the exact preview only for the protocol's automatically effective competing-instruction exception. Replace any effective legacy boot-pair, global-state, or milestone-maintenance rule; do not stack competing startup instructions. Report other project-document drift separately unless the user explicitly authorizes those exact repairs.

Existing important Markdown is registered by read condition, path, and the subject/truth it contributes. It does not need a Thuban marker or rename. Thuban-owned project documents use the names and markers defined in the protocol.

Prefer an existing subject owner to another durable Markdown. Create one only for a distinct owner, recurring consumer, and real lifecycle; do not persist chat logs, transient reasoning, or default handoff, memory, or latest-status files. Treat human- or organization-authority documents as protected unless the current task explicitly includes editing them. This restraint does not add a second confirmation to an explicitly requested ordinary document edit unless governance, structure, or destructive disposition also changes.

Ordinary task work may synchronize only verified local state and mechanically changed route paths under the root node's narrow maintenance rule. Status evidence does not authorize adding, removing, or changing priority, queue membership, or `Next`; those require the user or an approved plan. Governance decisions require `$thuban` again.

## Skill routing

Do not create a Skill pool by default. Read [THUBAN-SKILLS.md](references/THUBAN-SKILLS.md) only when the user asks about project Skills, an existing router is audited or repaired, or repeated capability selection has demonstrated routing cost.

## Update and report

React to evidence-bearing events: boundary or authority changes, material verified state changes, document conflicts, repeated recovery failures, structure changes, or relevant capability decisions. Do not schedule ceremonial monthly reviews or touch timestamps to imply freshness. No changed truth means zero diff.

Lead reports with the verdict. Then state evidence and uncertainty, changed versus proposed actions, approvals still required, and validation. Scale the report to the consequence; a clean maintenance pass may be one sentence.
